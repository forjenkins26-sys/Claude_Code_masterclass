00 · The problem

A basic RAG pipeline falls over on a real QA corpus

The starter version of this demo did the textbook thing: chunk the documents, embed each chunk with one model, store the vectors, and on a question return the four nearest neighbours. On a handful of PDFs that works well enough to teach the idea.

A test-case library breaks it in a specific way. Ask “which tests expect a 429?” and a dense embedding model has no strong signal for the literal token 429 — it encodes meaning, and the meaning of “rate limit exceeded” is spread across many rows that never mention the number. Meanwhile the four nearest neighbours are frequently four executions of the same scenario on four different browsers, because that is what a real suite looks like.

So this version adds three things a basic pipeline does not have: a second retrieval leg that matches on exact tokens, a fusion step that merges the two ranked lists honestly, and a re-ranking model that reads the question and the candidate together before deciding what the language model sees.

01 · The corpus

5,000 test cases, and only 344 distinct ideas

The corpus is generated by a seeded script, not written by a language model, so it is identical on every run and costs nothing to rebuild. Its shape is the interesting part, and it is deliberate.

There are 344 hand-written scenarios — a feature paired with something a tester actually does to it, each with its own expected result. Each scenario is then executed across 16 contexts: eight browser/device combinations, three plan tiers, three roles and two environments. 344 × 16 gives 5,504 candidate rows, trimmed to 5,000.

One rule holds the generator honest: no scenario is ever emitted twice. Ask it for more rows than 344 × 16 and it refuses rather than repeating itself, because a corpus padded with duplicates makes every retrieval number look better than it is.

02 · Chunking

One test case is one chunk, and that size was measured

Chunking a PDF means guessing where a thought ends. A table does not have that problem: the row boundary already is the boundary of a complete idea. Four columns — Summary, Description, Test Steps, Expected Result — are concatenated with their column names kept as labels, and that assembled document is the chunk.

Keeping the label matters more than it looks. Without it, “Expected Result: HTTP 403 is returned” flattens to bare text, and the word “expected” in someone’s question has nothing to match against on the lexical leg.

03 · Embedding

One model pass produces both vectors

The usual way to build hybrid search is a dense encoder plus a separate BM25 index: two vocabularies, two tokenisers, two things to keep in sync as the corpus changes. BAAI/bge-m3 avoids that entirely — a single forward pass returns a dense vector and a sparse one, from the same tokenisation of the same text.

Dense1,024 floats

Compared with cosine distance. Position in the space encodes meaning, so paraphrases land near each other even with no shared words.

Finds “visitor is not bucketed” when you asked about “users excluded from the experiment”.

Sparseone weight per distinct token

A learned weight per token that occurs in the text; everything else is implicitly zero. Scored by overlap, like a smarter BM25.

Finds the row containing the literal string 429, Retry-After or VWO-TC-04271.

04 · Query rewriting

Ask the question several ways before searching

A tester and a test case rarely use the same words. Before any vector is computed, the question goes to the language model once and comes back as a small set of alternate phrasings — one leaning on product vocabulary, one reduced to keywords for the lexical leg to bite on.

If that call fails, the pipeline searches the original question alone rather than erroring. A rewrite is an optimisation, and losing it should cost recall, not the answer.

05 · Retrieval

The two legs disagree, and that is the point

Both legs run against one Qdrant collection holding two named vectors per point, so a chunk has one id, one payload and one lifecycle. Hits from either leg can be merged by id with no join, and a metadata filter written once applies to both.

The app shows the overlap count on every query. A low overlap is the case for hybrid search: each leg is reaching rows the other misses. If the two lists agreed completely, the second leg would be dead weight.

06 · Fusion

Fuse the rankings, never the scores

Dense cosine similarity comes back around 0.82. The sparse leg returns something like 14.7. Those numbers are not on a shared scale, and averaging them is meaningless — whichever leg happens to produce bigger numbers would quietly win every time.

Reciprocal Rank Fusion discards the magnitudes and keeps only the ordering. Each list contributes 1/(k+rank) for the documents it returned, and the contributions are summed per document.

Because RRF never looks at a score, it needs no normalisation step and no tuned per-leg weight — the two things that make most hybrid setups fragile when the corpus changes.

07 · Re-ranking

A model that reads the question and the candidate together

Everything up to here used a bi-encoder: the question and the chunk are embedded separately, and can only be compared afterwards through a dot product. That is what makes searching 5,000 chunks fast — the chunk vectors were computed once, at ingest.

BAAI/bge-reranker-v2-m3 is a cross-encoder. It takes the question and one candidate as a single input and reads them jointly, so it can judge relevance the bi-encoder could only approximate. That is also why it cannot run over the whole corpus: it only ever sees the fused top candidates.

One detail worth stating: the reranker always scores against the original question, never a rewrite. The rewrites exist to widen recall; judging relevance against a paraphrase would optimise for the paraphrase instead of for what was asked.

08 · Generation

Grounded, cited, and willing to say no

Four chunks reach the language model, numbered, each carrying its issue key and module. The system prompt allows only those chunks as source material, requires [Chunk N] citations inline, and requires the model to say the context does not contain the answer rather than filling the gap from its own knowledge of the product.

There is a second mode. A request shaped like “create a test case for VWO-1234 covering webhook retries” is detected by intent and switches the prompt: the retrieved rows become format and style templates rather than facts to quote, and the output is a structured test case in the conventions the corpus already uses.

09 · The stack

What runs, and where

Flask + SSE Four pages, no build step. Ingestion progress streams as Server-Sent Events — one-directional traffic, so no websocket earns its keep.
bge-m3 Runs locally through FlagEmbedding. Dense plus sparse from one pass. First run downloads about 2.3 GB into the Hugging Face cache.
bge-reranker-v2-m3 Local cross-encoder, roughly 570 MB. Sees only the fused candidates, never the corpus.
Qdrant Embedded by default — a local folder, no Docker, no server to start. Point QDRANT_URL at a real server and the same code runs against it.
Groq The only network call in the pipeline: query rewriting and the final answer. Everything else is on your machine.

The embedding and re-ranking models are the reason the first query is slow and every later one is fast. Both loaders are lazy and locked, so the port opens immediately and two simultaneous requests cannot each pull a copy of a multi-gigabyte model into memory.

10 · Knobs

Six values worth turning during a workshop

CHUNK_SIZE 1400

Measured to keep all 5,000 rows whole. Set it to 1000 to split 77 % of them and see what a mid-document boundary costs.

CHUNK_OVERLAP 150

Characters repeated between adjacent chunks. Only does anything once a document is long enough to split.

TOP_N_HYBRID 20

Candidates per leg per query variant. Raising it widens recall and gives the reranker more to chew on — at a cost in latency.

TOP_K_RERANK 4

Chunks that reach the language model. Small on purpose: more context is not more grounding.

RRF_K 60

Fusion smoothing. Lower it and a single confident leg starts winning again; raise it and agreement across legs dominates.

REWRITE_ENABLED on

Turn it off and ask a question phrased unlike the corpus. The recall drop is the demonstration.

11 · Limits

What this does not do

Stated plainly, so nobody is surprised

The chunk viewer’s text search is page-local. Qdrant has no substring operator, so “contains” is applied in Python after the scroll. Honest at 5,000 rows; at corpus scale it needs a full-text payload index.

Payload indexes do nothing in embedded mode. Local Qdrant filters by scanning. The indexes are declared for the day someone sets QDRANT_URL, and the client says so in a warning on startup.

Nothing here is evaluated. There is no retrieval metric, no golden set, no measurement of whether the reranker helps on this corpus. The page shows you the mechanism so you can judge it yourself; it does not claim a score.

The corpus is synthetic. The scenarios are written to read like real VWO test cases, and the generator refuses to repeat one — but no part of it was harvested from a production test suite.
